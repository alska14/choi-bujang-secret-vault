# 방어전 단계별 기록

일부러 뚫려 있는 가상 자료실을 한 단계씩 막아 가는 과정입니다. 각 단계에서 무엇이 문제였고, 무엇을 바꿨고, 어떻게 확인했는지, 아직 남은 약점이 무엇인지 적었습니다. 자세한 확인 결과와 다시 실행하는 법은 [README.md](../README.md)의 단계별 절에 있습니다.

이 문서에는 비밀번호, 토큰, API 키 값을 적지 않습니다. 키는 모두 Vercel 환경변수에만 있습니다.

## 한눈에 보기

| 단계 | 막으려는 것 | 한 일 | 핵심 파일 |
|---|---|---|---|
| 1 | 출발점 | 시작 틀을 배포. 일부러 뚫린 자료실을 확인 | `public/data.json` |
| 2 | 자료가 코드에 그대로 공개됨 | 가상 메모를 Supabase DB로 옮기고 서버 함수로 읽음 | `api/notes.js`, `src/notes-api.mjs` |
| 3 | 로그인 없이 누구나 읽음 | 진짜 로그인과 토큰 검사 | `src/verify-login.mjs`, `src/auth-api.mjs` |
| 4 | 로그인해도 남의 메모가 보임 | 소유자 비교 | `src/notes-api.mjs` |
| 5 | 브라우저가 DB를 직접 부를 수 있음 | 요청을 서버 한곳으로 모으고 직접 권한 회수 | `db/revoke-direct.sql`, `src/auth-api.mjs` |
| 6 | 등록 안 된 기기에서 자료를 받음 | 등록된 기기만 허용하는 판정 규칙 | `src/decider.mjs` |
| 7 | 평소와 다른 접속을 그냥 통과시킴 | 위험 신호가 겹치면 다시 확인 요구 | `src/decider.mjs` |
| 8 | 같은 계정으로 다른 구역 자료까지 열림 | 자료를 구역(자원 ID)으로 나누고 판정기에 경로·동작 규칙 추가 | `src/decider.mjs`, `test/decider-zones.test.mjs` |
| 9 | 탈취된 계정이 조용히 대량 조회해도 모름 | 조회 폭주를 탐지해 권한 회수를 제안 | `src/detect.mjs` |
| 10 | 침해로 바뀐 메모와 정책을 되돌려야 함 | 검증한 사본으로 정책 복원, 지정한 메모 한 건 복원 | `scripts/policy-restore.mjs`, `src/restore-api.mjs` |
| 보너스 xdr-01 | 무차별 로그인 공격 | 경보를 block·alert·record로 분류 | `xdr/brute-force/` |
| 보너스 xdr-02 | 웹 주입 공격 | 같은 방식으로 웹 요청 경보 분류 | `xdr/web-injection/` |

11단계 이후와 나머지 보너스(`known-cve`, `persistence`, `privilege`, `exfiltration`)는 아직 하지 않았습니다.

## 1단계: 일부러 뚫린 출발점

시작 틀을 Vercel에 배포하면 `/data.json`에 가상 메모가 그대로 공개됩니다. 이 상태가 문제의 출발점이고, 이후 단계가 하나씩 막습니다. 저장소는 공개(Public)여야 하고, 가상 메모에는 실제 개인정보를 넣지 않습니다.

## 2단계: 자료를 코드 밖으로 옮김

- 문제: 메모가 `data.json`과 Git 이력에 그대로 있었습니다.
- 한 일: 메모를 Supabase `notes` 테이블로 옮기고, 화면은 `/api/notes` 서버 함수로 읽게 했습니다. 서버 함수는 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`를 환경변수에서만 읽습니다.
- 확인: 배포된 `/`, `/data.json`에 메모 문장이 없고, GitHub 최신 파일에서도 검색되지 않습니다.
- 남은 약점: 옛 커밋 `93f6d0e`에는 메모가 남아 있습니다. 이력까지 지우지는 않았습니다.

## 3단계: 진짜 로그인

- 문제: `/api/notes`를 로그인 없이 누구나 부를 수 있었습니다.
- 한 일: Supabase Auth 이메일·비밀번호 로그인을 붙였습니다. 서버가 요청의 `Authorization: Bearer` 토큰을 검사하고, 없거나 틀리면 401을 돌려줍니다. 브라우저가 보낸 사용자 ID는 믿지 않고 검증된 ID만 씁니다.
- 확인: 로그인 없이 `/api/notes`를 요청하면 401과 JSON 오류가 나옵니다.
- 남은 약점: 로그인은 신원 확인일 뿐이라 남의 메모 접근은 아직 막지 못했습니다.

## 4단계: 로그인해도 내 자료만

- 문제: 로그인한 B가 A의 메모 ID를 알면 읽고 고치고 지울 수 있었습니다.
- 한 일: 검증된 사용자 ID와 DB의 `owner_id`를 비교합니다. 남의 메모와 주인 없는 메모는 존재 여부도 알리지 않도록 404로 거부합니다. 추가할 때 `owner_id`는 확인된 사용자 ID로 저장합니다.
- 확인: 가짜 인증과 가짜 DB로 소유자 검사를 시험했습니다(`node --test test/notes-api.test.mjs`).
- 남은 약점: 서버 전용 키는 RLS를 거치지 않아서, 소유자 비교가 코드에서만 지켜집니다.

## 5단계: 요청을 서버 한곳으로

- 문제: 브라우저에 Supabase 공개 키가 있어 DB를 직접 부를 수 있었습니다.
- 한 일: 브라우저는 `/api/auth`, `/api/notes` 서버 함수만 부릅니다. 로그인도 서버가 대신 받습니다. `notes` 테이블의 `public`, `anon`, `authenticated` 직접 권한을 모두 회수했고, 심판이 읽도록 `/aleph.json`에 `originalApiUrl`, `allowedRoutes`, `identityProvider`를 기록합니다.
- 확인: 공개 키로 원본 REST 주소를 직접 부르면 HTTP 401입니다. 화면 코드에서 키 문자열 검색 결과가 0건입니다.
- 남은 약점: `/api/auth`는 자체 횟수 제한이 없어 비밀번호 대입 방어를 Supabase 기본 제한에 기댑니다. 토큰은 브라우저 `localStorage`에 저장됩니다.

## 6단계: 등록된 기기만 자료실에

- 문제: 도둑이 비밀번호를 훔쳐 로그인하면 등록되지 않은 기기에서도 자료를 받을 수 있었습니다.
- 한 일: `src/decider.mjs`에 `device_registered` 규칙을 추가했습니다. 반 엔진이 확인해 넘긴 `deviceRegistered`가 정확히 `true`이고 읽기(GET)일 때만 허용합니다. `false`나 값 없음은 `device_not_registered`로 거부합니다.
- 알아둘 점: 로그인을 막는 게 아니라 로그인 뒤의 자료 요청을 막습니다. 기기가 실제로 등록됐는지는 엔진이 확인하고, 이 코드는 그 값으로 허용·거부만 정합니다.
- 확인: `npm run decider:test`에서 등록 기기 통과, 미등록 기기 거부를 확인했습니다. 심판 판정은 괴물 4마리 모두 격파로 표시됐습니다.
- 남은 약점: 등록 기기의 GET이 아닌 요청은 기본 거부로 남습니다.

## 7단계: 평소와 다른 접속은 다시 확인

- 문제: 등록 기기라도 낯선 지역·시각·네트워크로 접속하는 경우를 그대로 통과시켰습니다.
- 한 일: `step_up_required` 규칙을 추가했습니다. 위험 신호가 둘 이상 겹칠 때만 `step_up`(추가 본인 확인 요구)을 돌려줍니다. 신호는 지역 `foreign`, 네트워크 `unusual`, 새벽 0~5시, `risk_signal` 이벤트 10건 이상입니다. 신호 하나만으로는 막지 않습니다.
- 재인증: 엔진이 확인해 넘긴 `stepUp.verified`가 `true`이고 나이가 0~900초일 때만 인정합니다. 값이 없거나 오래되면 인정하지 않습니다.
- 입력 검사: 판정기는 엔진이 검증해 넘긴 요청 필드만 읽습니다. 값이 없거나 `unknown`이면 위험으로 세지도, 정상값으로 채우지도 않습니다.
- 확인: `npm run decider:test` 4개 통과. 심판 판정은 통과했습니다.
- 남은 약점: 엔진이 실제로 자료를 막고 새 로그인 뒤 다시 판정하는 경로는 시험하지 못했습니다.

## 8단계: 자료마다 갈 수 있는 구역을 나눔

- 문제: 같은 계정으로 로그인하면 자기 메모, 강사 공지, 다른 사람의 자료까지 같은 권한으로 열릴 수 있었습니다. 괴물은 다른 구역 메모의 API 조회·수정·목록 조회, 학생 계정으로 강사 공지 수정입니다.
- 구역 표: 판정기가 경로 모양을 구역으로 묶습니다. 내 메모(`my-notes`)와 반 공지(`class-notices`)는 읽기만 열고, 강사 자료는 열지 않습니다. 표에 없는 경로(전체 목록, 모르는 경로, `export` 같은 기능 경로)는 모두 거부합니다.
- 쓰기 거부: 추가·수정·삭제는 구역과 관계없이 거부합니다. 일반 학생의 공지 수정도 여기서 막힙니다.
- 자료 API 이중 확인: API도 검증된 사용자와 저장된 `owner_id`를 다시 비교합니다. 본문·쿼리에 `role`, `owner_id`를 끼워 넣어도 읽지 않습니다.
- 확인: 구역 규칙 시험과 직접 API 시험을 추가했고(가상 요청·가짜 DB) 모두 통과했습니다.
- 남은 약점: 요청 계약에 메모 주인이 없어 판정기는 본인 메모 수정도 허용하지 않습니다. 화면의 목록 경로(`GET /api/notes`)는 구역 표에 없어 엔진 경로에서는 거부됩니다.
- 첫 제출(36점)에서 `S08_OTHER_ZONE_ALLOWED`가 나왔습니다. 원인으로 본 것: 설정의 `allowedRoutes`가 구역 없이 쓰기·목록 경로까지 열고 있었습니다. 보완으로 `allowedRoutes`를 구역이 선언된 읽기 경로 4개로 줄이고, 그 경로(`/api/my/notes`, `/api/notices`)를 실제로 추가했습니다.

## 9단계: 도플갱어를 찾고 권한을 거둠

- 문제: 허용·거부 기록이 흩어져 있으면 가짜 사용자(도플갱어)의 첫 의심 요청부터 탐지·회수까지 얼마나 걸렸는지 알 수 없습니다.
- 한 일: `detect(events)`가 같은 사용자의 조회(GET)가 10분 안에 120건을 넘으면 `propose_revocation`(이유 `burst_read`, 대상 `subject`)을 제안합니다. 120건 이하, 다른 사용자 합산, 10분 밖의 사건은 제안하지 않아 정상 사용자는 유지됩니다.
- 입력 처리: 사건에서 시각·요청 종류·가명 사용자만 읽고, 메모·토큰·실명은 저장하거나 출력하지 않습니다. 형식이 틀린 사건은 버립니다.
- 확인: `npm run detect:test` 6개와 추가 시험 7개가 통과했습니다(가상 사건, 심판 판정 아님).
- 남은 약점: 실제 회수와 재접속 차단은 엔진과 심판이 확인하며 이 저장소에서는 시험하지 못했습니다. 프롬프트의 네트워크 조건은 계약에 값이 없어 구현하지 않았습니다.

## 10단계: 백업에서 자료실을 되살림

- 문제: 3차 침공으로 가상 메모와 안전 정책이 함께 바뀌면 화면을 새로고침해도 내용과 권한이 돌아오지 않습니다. 괴물은 B의 메모를 변조하거나 삭제한 뒤 복구 경로를 부르거나, 복구 직후 1~9단계 공격을 다시 보내는 것입니다.
- 정책 복원: 9단계를 통과한 커밋에서 만든 안전 정책 사본(버전, 허용 경로, 정책 파일 해시, 봉인 해시)과 현재 시험 정책의 차이를 먼저 보여 줍니다. 사본이 없거나 검증에 실패하면 중단하고, `--apply`를 붙였을 때만 바뀐 항목만 되돌립니다. 다른 서비스 규칙과 감사 이력은 건드리지 않습니다.
- 한 건 복원: `POST /api/restore/:noteId`가 비공개 사본에서 지정한 메모 한 건만 복원합니다. 로그인한 본인의 메모만 대상이고, 복원 뒤 ID·소유자·내용 해시를 사본과 다시 대조합니다. 사본이 없거나 조작됐으면 복원하지 않고 중단합니다.
- 확인: 정책을 일부러 망가뜨렸다가 되돌리는 연습과 한 건 복원 시험을 했고(가짜 DB), 되돌린 뒤 판정기 시험도 통과했습니다.
- 남은 약점: 운영 사본을 아직 만들지 않아 배포된 복원 경로는 로그인 뒤에도 사본 없음으로 중단합니다. 실제 DB에서의 변조·삭제 복원은 시험하지 못했습니다.

## 보너스 xdr-01: 무차별 로그인 공격

경보 28건을 보고 block(차단 후보), alert(알림), record(기록)로 분류합니다. 결과는 block 10, alert 9, record 9이고 판정 100점입니다.

- `read-alerts.mjs`: 경보에서 필요한 필드만 뽑습니다.
- `patterns.json`: 공격 모양을 이름·조건·근거 한 줄로 정리했습니다(MITRE T1110).
- `decide.mjs`: 확신도 0.85 이상은 block, 0.5 이상은 alert, 그 아래는 record입니다. 애매한 경보만 Jev(TypeSafe)에 물어 확신도를 올릴 수 있고, 응답이 없으면 alert로 남습니다. Jev 키는 환경변수 `TYPESAFE_API_KEY`입니다.
- `respond.mjs`: 알림은 `xdr/alerts.log`에 한 줄씩, 차단 후보는 만료 시각과 근거 경보 번호를 붙여 `block-rules.json`에 적습니다.

세 번 연속 0점이 나온 뒤에 `decide.mjs`를 외부 파일 없이 혼자 동작하는 한 파일로 바꾸고, 위험도 10 이상은 차단, 5~9는 알림이라는 바닥 기준을 넣었더니 통과했습니다. 정확한 원인은 확정하지 못했습니다.

## 보너스 xdr-02: 웹 주입 공격

같은 구조로 경보 26건을 분류합니다. 결과는 block 8, alert 9, record 9이고 판정 100점입니다. 패턴은 SQL 구문 반복, 스크립트 태그 반복, `../` 경로 거슬러 올라가기 반복, 명령 구분자 연속, 주입 표식 반복입니다(MITRE T1190).

## 이 과정에서 배운 것

- 방어는 한 겹이 아니라 겹겹입니다. 로그인(3), 소유자(4), 직접 접근 차단(5), 기기(6), 이상 징후(7)가 각각 다른 구멍을 막습니다.
- 판정자가 격리된 환경에서 코드를 따로 실행할 수 있어서, 보너스 `decide.mjs`는 다른 파일에 기대지 않는 단독 파일이어야 했습니다.
- 로컬 시험(`decider:test`, 변형 경보 시험)은 연습입니다. 실제 엔진 경로와 심판 판정을 대신하지 못합니다.
