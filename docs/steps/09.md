# 9단계: 도플갱어를 찾고 권한을 거둡니다

커밋: `243b31a`
심판 결과: 만점

## 무엇이 문제인가

6~8단계는 입구에서 막는 규칙이었습니다. 입구를 통과한 도플갱어가 조용히 자료를 대량으로 읽으면 알아채지 못합니다. 허용·거부 기록이 흩어져 있으면 가짜 사용자의 첫 의심 요청부터 탐지·회수까지 얼마나 걸렸는지 알 수 없습니다. 실제 사고로 페이스북 이용자 5억 3,300만 명의 정보가 긁혀 유출된 사례가 소개됩니다.

## 이어받기

README의 마지막 단계 기록(8단계)과 마지막 커밋이 맞는 것을 확인했습니다. 시작 틀의 `src/detect.mjs`는 어떤 접속도 회수하지 않는 기본값이었고, 사건 계약은 `docs/DETECT_EVENTS.md`에 있었습니다.

## 제작 1: 입력 정리

**프롬프트가 시킨 것**: 제공된 가상 사건에서 가명 사용자·기기·요청 종류·판정만 읽도록 입력을 정리한다. 메모 내용·토큰·실명은 저장하거나 출력하지 않는다. 이번에는 입력 처리만 바꾼다. 확인: 정상 사건과 의심 사건을 비밀값 없이 읽을 수 있어야 한다.

**한 일**: 사건에서 시각(`at`), 요청 종류(`method`), 가명 사용자(`identity.sub`)만 읽습니다. 계약의 사건에는 이 세 값만 있습니다. 그 밖의 값(토큰, 메모 내용, 실명 등)은 읽지도 저장하지도 출력하지도 않고, 결과에도 넣지 않습니다. GET이 아니거나 형식이 틀린 사건은 세지 않고 버리며, 정상값으로 채우지 않습니다.

## 제작 2: 탐지 규칙 하나

**프롬프트가 시킨 것**: 평소와 다른 네트워크와 갑작스러운 다량 조회가 함께 나타날 때만 의심으로 표시하는 탐지 규칙 하나를 넣는다. 지역 하나만으로 확정하지 않고 정상 사건은 그대로 둔다. 확인: 복합 의심 사건만 탐지되고 정상 사건은 유지된다.

**한 일**: 같은 사용자의 GET 조회가 어느 10분 구간에서든 **120건을 넘을 때만** 의심으로 봅니다. 정확히 120건은 제외합니다. 다른 사용자는 합산하지 않고 10분 밖의 사건은 같은 묶음으로 세지 않습니다. 시간 순서가 아니어도 사용자별로 정렬해서 셉니다. "10분 안"은 10분짜리 자를 시간축에 대고 밀면서, 어느 위치에서든 자 안에 121건이 들어오는지 보는 방식입니다.

**프롬프트와 다르게 한 점**: 프롬프트는 "평소와 다른 네트워크가 함께 나타날 때만"이라고 했지만, 계약의 사건에는 네트워크 값이 없습니다. 계약에 없는 값은 쓰지 않기로 해서, 규칙은 계약(`docs/DETECT_EVENTS.md`)대로 조회 폭주 하나입니다.

## 제작 3: 회수 제안

**프롬프트가 시킨 것**: 탐지한 사건의 별도 결과에 `propose_revocation` 제안을 넣는다. 대상은 확인된 가상 기기 한 개로 한정하고 이유 코드를 함께 남긴다. 기존 접속 허용·거부 응답 형식은 바꾸지 않는다. 회수 API를 직접 만들지 않는다. 실제 회수와 시간은 심판이 확인한다. 확인: 의심 사건은 대상과 이유가 있는 회수 제안을 내고, 정상 사건은 내지 않아야 한다.

**한 일**: 의심이면 `{ action: 'propose_revocation', reasonCode: 'burst_read', subject }`를, 아니면 `{ action: 'observe' }`를 돌려줍니다. 회수 API는 만들지 않았고, 판정기(`src/decider.mjs`)와 기존 응답은 바꾸지 않았습니다. 파일은 다른 파일을 불러오지 않는 단독 파일입니다.

**프롬프트와 다르게 한 점**: 사건에 기기 값이 없어서, 대상은 계약이 정한 `subject`(가명 사용자) 하나입니다. 기기 한 개로 한정하는 부분은 구현하지 않았습니다.

## 제출 전 확인

`9단계 저장점`으로 커밋하고 `npm run bundle`을 실행했습니다. 자기 점검에 `burst_read`를 추가했고, 탐지 함수를 직접 실행한 결과이며 엔진 회수가 아니라고 밝혔습니다.

## 쉽게 풀면

6~8단계가 입구 경비라면, 9단계는 건물 안 CCTV를 보는 사람입니다. 한 사람이 갑자기 서류를 수백 장 뽑아 가면 "저 사람 이상한데?" 하고 알립니다.

- 철수가 10분에 30번 읽음: 정상
- 철수가 10분에 정확히 120번: 정상(경계는 봐줌)
- 철수가 10분에 121번: 회수 제안
- 철수 100번과 영희 100번: 정상(둘을 합쳐 200번으로 세지 않음)
- 철수가 200번 읽었지만 7초 간격이라 10분 안에는 86번뿐: 정상

우리 코드는 회수를 **제안만** 합니다. 실제로 권한을 거두는 일은 엔진이 합니다.

## 괴물 4마리

| 괴물 | 시험 내용 | 누가 맡나 |
|---|---|---|
| 대구 | 합성 도플갱어 접속 사건을 기록과 탐지기에 입력 | 우리 `detect` |
| 제주 | 회수된 신원으로 다음 요청을 재시도 | 엔진 |
| 지역 미정 | 회수 뒤 남은 탈취 세션으로 재접속 | 엔진(세션 무효화) |
| 목포 | 회수된 도플갱어가 다른 자원으로 이동 | 엔진 |

"회수 뒤 남은 세션으로 재접속"은, 권한을 회수해도 이미 발급된 로그인 증표(세션·토큰)가 살아 있으면 도둑이 그걸로 다시 접속하는 공격입니다. 회수할 때 기존 세션까지 무효화해야 막힙니다.

## 하지 못한 것과 남은 약점

- 실제 회수 집행, 회수된 신원의 재시도, 남은 세션의 재접속, 다른 자원으로 이동은 엔진이 집행하고 심판이 확인합니다. 이 저장소에서는 시험하지 못했고 README에 **엔진 연결·실제 회수 미실행**으로 적었습니다.
- 임계값 120건·10분은 연습 계약의 값이며 실제 사용자 행동으로 조정하지 않았습니다.
- `npm run detect:test` 6개와 추가 시험 7개는 가상 사건 연습이며 심판 판정이 아닙니다.
