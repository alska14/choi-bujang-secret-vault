# 보너스 xdr-03: 알려진 취약점 악용을 잡아 냅니다

커밋: 보너스 xdr-03 저장점
심판 결과: 아직 제출하지 않았습니다.

## 무엇이 문제인가

최 부장 PC의 오래된 로그 라이브러리로 원격 명령을 불러오는 요청이 들어옵니다. 이미 공개된 취약점(CVE)을 노린 공격입니다. 실제 사고로 2021년 12월 아파치 로그4j(Log4Shell)의 원격 코드 실행 취약점(CVE-2021-44228)이 공개된 직후 전 세계에서 대규모 악용 시도가 벌어진 사례가 소개됩니다.

만들 것은 공개된 취약점 목록과 공격 기법 목록을 보고, 들어오는 요청이 알려진 악용 형태인지 판단해 알리고, 형태가 뚜렷한 요청만 막을 후보로 올리는 모듈입니다. 판정기 규칙을 대신하지 않습니다.

## 이어받기

README의 마지막 단계 기록(12단계 보완)과 마지막 커밋이 일치하는 것을 확인했습니다. `xdr/known-cve/`는 비어 있었고 경보 묶음은 24건(`xdr/fixtures/known-cve.json`)이었습니다. 아무 파일도 고치지 않았습니다.

## xdr-01·02와 달라진 점

이번 프롬프트는 앞의 두 모듈보다 판정 파일에 더 엄격합니다. xdr-01에서 0점을 세 번 받고 배운 것을 처음부터 적용했습니다.

- Jev를 부르지 않습니다. 심판이 인터넷 없이 `decide.mjs`만 불러와 경보마다 바로 답을 받기 때문에 바깥에 묻지 않고 혼자 계산합니다.
- `decide.mjs`에 import 문이 없습니다. 다른 파일이나 패키지를 불러오지 않고, 파일을 읽거나 쓰지 않고, 네트워크도 쓰지 않습니다. 패턴은 파일 맨 위 상수로 넣었습니다.
- 읽기 모듈은 확인용이라 `decide.mjs`가 불러오지 않는 별도 파일입니다.
- 경보의 원격 조회 구문은 문서용 표기이므로, 이 문자열을 다른 곳에 넣거나 바꾸지 않습니다. 탐지에 쓰기만 하고 로그·결과·이유에는 담지 않습니다.

## 제작 1: 경보 읽기

**프롬프트가 시킨 것**: `xdr/fixtures/known-cve.json`의 Wazuh 경보를 읽어 시각·출발 주소·계정·규칙 수준·설명만 뽑는 읽기 모듈을 `xdr/known-cve/read-alerts.mjs`로 만든다. 원본 경보는 고치지 않고 비밀값처럼 보이는 값은 출력하지 않는다. 이 모듈은 확인용이라 `decide.mjs`가 불러오지 않게 따로 둔다. 확인: 경보 건수와 뽑은 줄 수가 같아야 한다.

**한 일**: 경보 24건에서 24줄을 뽑습니다. 요청 주소와 머리글(조회 구문이 들어 있을 수 있음)은 뽑지도 출력하지도 않습니다. 출력에 조회 구문은 0건입니다.

## 제작 2: 패턴 목록

**프롬프트가 시킨 것**: 이 공격의 알려진 형태를 `xdr/known-cve/patterns.json`으로 정리한다. 근거는 CVE-2021-44228 형태 요청, MITRE ATT&CK T1190이고 신호는 요청 머리글·인자 안의 원격 조회 구문(jndi 형태), 알려진 취약점 점검 도구의 흔적 정도다. 패턴마다 이름·찾는 조건·근거를 한 줄씩 적고 근거 없는 패턴은 넣지 않는다.

**한 일**: 패턴 7개를 근거 한 줄씩과 함께 정리했습니다.

| 패턴 | 확신도 | 뜻 |
|---|---|---|
| 높은 위험도의 취약점 악용 경보 | 0.90 | 위험도 10 이상 |
| 머리글 안의 원격 조회 구문 | 0.97 | 머리글(user-agent 등)에 jndi 형태 구문 |
| 요청 인자 안의 원격 조회 구문 | 0.95 | 주소·검색어에 jndi 형태 구문 |
| CVE-2021-44228 형태로 설명된 요청 | 0.90 | 경보 설명이 그렇게 밝힘 |
| 알려진 취약점 점검 도구의 흔적 | 0.60 | 탐색 단계, 단정하기 어려움 |
| 취약점 이름이나 단어만 있는 요청 | 0.55 | 수업 자료 검색일 수 있음 |
| 중간 위험도 경보 | 0.55 | 위험도 5~9 |

## 제작 3: 판정 모듈

**프롬프트가 시킨 것**: 패턴을 `decide.mjs` 맨 위에 상수로 옮겨 적고, 그 패턴과 경보를 맞춰 판단하는 `decide(alert)` 하나를 내보낸다. 반환은 `{action, confidence, reason}`이고 확신도는 경보가 패턴과 얼마나 뚜렷하게 맞는지를 0~1로 매긴 값이다. 0.85 이상은 block, 0.5 이상은 alert, 그 아래는 record다. `reason`에는 근거 패턴 이름을 한 줄로 적는다. 다른 파일이나 패키지를 불러오지 않고, 파일을 읽거나 쓰지 않고, 바깥에 묻지 않고 혼자 계산한다. 확인: 명확한 공격은 block, 애매한 건 alert, 정상 이벤트는 record로 나뉘어야 하고 `decide.mjs`에 import 문이 없어야 한다.

**한 일**
- `patterns.json`의 패턴과 같은 내용을 파일 맨 위 상수로 넣었습니다. 두 곳이 같은지 시험이 확인합니다.
- 경보 안의 모든 문자열 필드를 보고, 필드 이름이 머리글(user-agent, referer, 쿠키 등)이면 "머리글", 그 밖이면 "인자"로 구분해 원격 조회 구문을 찾습니다. 머리글과 인자 양쪽에 겹쳐 있으면 확신도를 조금 올립니다.
- 위험도 10 이상은 block, 5~9는 alert라는 바닥 기준을 처음부터 넣었습니다(xdr-01에서 통과한 표본의 기준).
- 이유(`reason`)에는 패턴 이름만 담고 요청의 값은 담지 않습니다. 입력 경보를 바꾸지 않고, 같은 입력이면 같은 답이 나옵니다.
- 이 파일은 `decide` 하나만 내보냅니다.

## 제작 4: 알림과 차단

**프롬프트가 시킨 것**: `xdr/known-cve/respond.mjs`를 새로 만들어, `decide` 결과 가운데 차단 후보만 ZTNA 판정기의 거부 규칙으로 넣는 연결을 만든다. 규칙에는 만료 시각과 근거 경보 번호를 붙이고 정상 사용자를 막는 규칙은 넣지 않는다. 알림은 같은 파일에서 `xdr/alerts.log`에 한 줄씩 쌓는다. `decide.mjs`는 판단 결과만 그대로 돌려주고 파일 쓰기·판정기 연결은 하지 않게 둔다. 판정기의 기존 규칙은 고치지 않는다.

**한 일**: `respond.mjs`가 알림을 `xdr/alerts.log`에 `[known-cve]` 접두사로 한 줄씩 쌓고(다른 모듈의 줄은 보존), 차단 후보를 `block-rules.json`에 적습니다. 후보는 7개 주소이고 규칙마다 만료 시각(경보 시각 + 1시간)과 근거 경보 번호가 있습니다. 같은 주소에서 정상(record) 판정이 난 적이 있으면 후보에서 뺍니다. `decide.mjs`는 파일을 쓰지 않습니다.

**프롬프트와 다르게 한 점**: 판정기(`src/decider.mjs`)의 요청에는 접속 주소가 없고 계약에 없는 필드를 만들면 안 되어서, 차단 후보는 파일로만 만들고 판정기에 연결하지 않았습니다(xdr-01·02와 같습니다).

## 제작 5: 시험 경보로 돌려 보기

**프롬프트가 시킨 것**: `npm run xdr:run -- known-cve`를 실행해서 `xdr/known-cve/result.json`을 만들고, block·alert·record 건수와 정상 이벤트를 block한 경우가 있는지 알려 준다.

**한 일**: 경보 24건이 block 8, alert 8, record 8로 나왔고 정상 이벤트를 막은 경우는 없습니다.

| 판정 | 건수 | 대상 |
|---|---|---|
| block | 8 | kc-01~08(위험도 10~13, 머리글·인자에 조회 구문) |
| alert | 8 | kc-09~16(위험도 5~8, 이름·단어만 있고 구문 없음) |
| record | 8 | kc-17~24(공개 화면, 상태 확인, 로그인 성공 등, 위험도 2~3) |

이 8/8/8은 문서에 적힌 정답이 아니라 우리 판정의 결과 건수입니다.

## 제출 전 확인

`npm run xdr:run -- known-cve`를 다시 실행해 `result.json`을 갱신하고 「보너스 xdr-03 저장점」으로 커밋합니다. 시험 10개(`xdr/known-cve/variants.test.mjs`)가 통과했습니다. 다른 위치·방식·대소문자의 조회 구문, 필드가 빠진 경보, `decide.mjs` 파일 하나만 빈 폴더에 복사해도 8/8/8이 나오는지, 소스에 import·파일·네트워크 사용이 없는지, 읽기 모듈이 조회 구문을 뽑지 않는지를 확인합니다.

## 쉽게 풀면

xdr-01이 "비밀번호를 계속 틀리는 사람", xdr-02가 "검색 칸에 이상한 명령어를 넣는 사람"이었다면, xdr-03은 "이미 널리 알려진 허점을 노리는 요청"을 찾는 것입니다. 로그4j 사고처럼 요청 머리글이나 주소 안에 원격으로 명령을 불러오는 특정 모양의 문자열이 들어 있으면 확실한 공격으로 봅니다. "CVE-2021-44228"이라는 이름만 있거나 수업 자료를 검색한 것은 공격이 아닐 수 있어서 알림만 남깁니다.

## 하지 못한 것과 남은 약점

- 차단 후보를 ZTNA 판정기에 실제로 연결하지 않았습니다. 후보는 파일로만 있고 실제 접속 차단은 일어나지 않습니다.
- 판정자의 정답표는 보지 못했습니다. 우리 기준이 정답표와 같다는 보장은 없습니다.
- 위험도가 낮은 경보에 조회 구문이 들어 있으면 block으로 봅니다. 조회 구문을 쪼개거나 인코딩해서 숨긴 변형은 탐지하지 않습니다(프롬프트의 신호 범위 밖이고, 문서용 표기를 변형하지 않는다는 규칙 때문입니다).
