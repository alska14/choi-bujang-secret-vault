# 2단계: 자료를 코드 밖으로 옮김

> 이 단계는 이전 작업에서 진행했습니다(커밋 `393629b`). 제작 프롬프트 원문은 이번 기록 작업에서 보지 못해서, README의 기록을 근거로 정리했습니다. 제작 번호는 나누지 않았습니다.

## 무엇이 문제인가

가상 메모가 `data.json`과 Git 이력에 그대로 들어 있었습니다. 코드 저장소를 보는 사람은 누구나 메모를 읽을 수 있었습니다.

## 한 일

- 메모를 Supabase의 `notes` 테이블로 옮겼습니다. 메모 본문은 Git에 올리지 않는 `db/seed.local.sql`에만 있습니다.
- 화면은 `/api/notes` 서버 함수로 메모를 읽습니다. 서버 함수는 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`를 Vercel 환경변수에서만 읽습니다.
- 테이블은 RLS를 켰고 `anon`, `authenticated`에 읽기 권한을 주지 않았습니다.
- 공개 `data.json`은 빈 목록으로 두고, 빌드가 복사하지 않게 했습니다.

## 쉽게 풀면

금고 안에 있던 서류를 꺼내 별도 보관소로 옮기고, 열쇠(서버 전용 키)는 서류 위에 두지 않고 관리실(환경변수)에 맡긴 단계입니다.

## 확인한 방법 (2026-10-06)

메모 문장이 공개 파일에 남았는지 세 군데를 봤습니다.

1. 현재 배포의 `/`, `/data.json`, `/aleph.json`을 로그인 없이 요청해 메모 문장이 있는지 봅니다. 메모 문장은 없었고, `/aleph.json`에는 확인 표시 `SAMPLE_NOTE_1`만 있었습니다.
2. 푸시한 뒤 `git grep -nE "실습용 가[상] " origin/main`으로 GitHub 최신 파일을 검색했습니다. 결과가 없어야 합니다.
3. `/api/notes`를 로그인 없이 요청해 응답을 봤습니다.

## 남은 약점

- 옛 공개 커밋 `93f6d0e`의 `data.json`에는 메모 문장 4건이 그대로 남아 있습니다. 최신 파일에서 지워도 Git 이력에는 남습니다.
- 옛 배포 주소는 Vercel 안내 화면만 응답해서 메모가 남았는지 확인하지 못했습니다. 옛 배포를 지웠다고 확인한 것은 아닙니다.
- 2단계 시점에는 `/api/notes`가 로그인 없이 누구나 부를 수 있는 공개 주소였습니다. 3단계에서 막았습니다.
