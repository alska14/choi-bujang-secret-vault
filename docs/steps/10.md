# 10단계: 백업에서 자료실을 되살립니다

커밋: `a07bb74`
심판 결과: 이 문서를 쓰는 시점에 결과를 받지 못했습니다.

## 무엇이 문제인가

3차 침공으로 가상 메모와 안전 정책이 함께 바뀌면, 화면을 새로고침해도 내용과 권한이 돌아오지 않습니다. 침입을 막는 것(1~9단계)과 별개로, 이미 망가진 뒤에 되살리는 방법이 필요합니다. 실제 사고로 깃랩 데이터베이스 삭제와 작동하지 않던 백업 사례가 소개됩니다.

## 이어받기

README의 마지막 단계 기록(9단계)과 마지막 커밋이 맞는 것을 확인했습니다. 강사 통과용 표본을 보니 복원 코드는 두지 않고 `restoreRoute`(`/api/restore/:noteId`) 선언과 절차만 적었습니다. 우리 설정은 `restoreRoute`가 `null`이었습니다.

## 제작 1: 정책 사본과 현재 정책의 차이

**프롬프트가 시킨 것**: 침해 전에 검증한 안전 정책 사본과 현재 시험 정책의 차이만 보여 주는 기능을 만든다. 사본이 없거나 검증에 실패하면 중단한다. 실제 운영 정책은 건드리지 않는다. 확인: 복원할 버전과 변경 범위가 실행 전에 보여야 한다.

**한 일**
- `backup/policy-snapshot.json`: 9단계를 통과한 커밋(`243b31a`)에서 만든 안전 정책 사본입니다. 정책 버전, 검증한 커밋, 허용 경로, 판정기·탐지 파일의 SHA-256, 사본 전체의 봉인 해시가 들어 있고 비밀값은 없습니다.
- `npm run policy:diff`: 복원할 버전과 변경 범위를 보여 줍니다. 아무것도 바꾸지 않습니다.
- 사본이 없거나 형식·봉인 해시 검증에 실패하면 중단하고 첫 이유를 출력합니다.
- 줄바꿈(CRLF/LF) 차이로 해시가 달라지지 않게 맞춘 뒤 계산합니다.

## 제작 2: 검증한 버전으로 되돌리기

**프롬프트가 시킨 것**: 검증한 안전 정책 버전으로 시험 정책을 되돌리는 절차를 붙인다. 다른 서비스 규칙과 감사 이력은 보존하고, 실행 전에 바뀔 항목을 확인하게 한다. 확인: B의 A 자료 요청은 다시 거부되고 A의 정상 요청은 유지되어야 한다.

**한 일**
- `npm run policy:restore`: 바뀔 항목만 보여 주고 실행하지 않습니다(기본).
- `npm run policy:restore -- --apply`: 검증을 통과하면 바뀐 항목만 되돌립니다. 정책 파일은 검증한 커밋의 내용을 `git show`로 읽어서 그 해시가 사본의 해시와 같을 때만 씁니다. 다르면 아무것도 쓰지 않고 중단합니다. 허용 경로는 `aleph.config.json`의 `allowedRoutes`만 바꾸고 다른 설정은 그대로 둡니다.
- 직접 해 본 순서: 판정기에 줄을 더하고 쓰기 경로를 선언해 정책을 일부러 망가뜨림, `policy:diff`로 2개 차이 확인, `policy:restore`로 미리보기, `--apply`로 적용, 다시 `policy:diff`에서 차이 0개. 되돌린 뒤 `decider:test` 4개와 `detect:test` 6개도 통과했습니다.

## 제작 3: 지정한 한 건만 복원

**프롬프트가 시킨 것**: 비공개 가상 메모 사본에서 지정한 한 건만 복원하는 POST 경로를 붙인다. ID·소유자·내용 해시를 대조하고 다른 메모와 감사 기록은 보존한다. 시험 계정 B의 메모로만 확인하고 서비스·경로를 README에 적는다. 확인: 복구 대상 한 건의 ID·소유자·내용 해시가 사본과 같아야 한다.

**한 일**: `POST /api/restore/:noteId`(서비스 notes, `aleph.config.json`의 `restoreRoute`)를 만들었습니다(`api/restore/[noteId].js`, `src/restore-api.mjs`).

1. 로그인을 확인합니다(없으면 401, POST가 아니면 405, ID가 UUID가 아니면 400).
2. 사본을 읽습니다. 사본이 없으면 복원하지 않고 503으로 중단합니다.
3. 호출한 사용자의 메모만 대상입니다. 사본에 없거나 남의 메모면 404입니다.
4. 사본 항목의 해시가 내용과 맞지 않으면 409로 중단합니다.
5. 지정한 한 건만 복원합니다. 이미 사본과 같으면 바꾸지 않고, 없으면 다시 만들고, 변조됐으면 제목·내용만 고칩니다. 소유자는 바꾸지 않고, 다른 사용자가 같은 ID를 쓰면 덮어쓰지 않습니다.
6. 복원 뒤 ID·소유자·내용 해시를 사본과 다시 대조합니다. 다르면 실패로 응답하고 다시 시도하지 않습니다.

비공개 사본은 서버 환경변수 `NOTES_BACKUP_JSON`(JSON 배열)에서만 읽고, Git에는 올리지 않습니다(`.gitignore`에 `backup/notes*.json`). 응답에는 메모 내용을 넣지 않고 `{id, restored, sha256}`만 돌려줍니다. 시험 9개는 가짜 DB로 B의 메모 변조 후 복원, 삭제 후 복원, 남의 메모, 사본 없음·조작, 복원 결과 불일치 등을 확인했습니다.

## 제작 4: 복원 뒤 재시험 순서

**프롬프트가 시킨 것**: 복구 뒤 1~9단계의 정상·금지 요청을 다시 실행할 순서를 README에 적는다. 실행하지 않은 시험은 미실행으로 두고 결과를 꾸미지 않는다. 확인: 자료와 정책이 돌아오고 이전에 막던 요청이 다시 거부되는지 볼 수 있어야 한다.

**한 일**: README에 6단계 순서를 적었습니다. `policy:diff`로 차이 0개 확인, `decider:test`, 구역 시험, `detect:test`, API 시험, `bundle` 순서입니다.

## 제출 전 확인

`10단계 저장점`으로 커밋하고, 배포를 기다린 뒤 `npm run bundle`을 실행했습니다(복원 경로 점검이 실제 배포를 보도록 순서를 바꿨습니다). 자기 점검에 `restore_unauth`(로그인 없는 복원 요청은 401), `policy_snapshot`(사본 검증)을 추가했습니다.

## 쉽게 풀면

침입을 막는 것은 1~9단계였고, 10단계는 이미 망가졌을 때 되살리는 단계입니다. 도둑이 서랍을 뒤집고 자물쇠 설정도 바꿨다면, 미리 찍어 둔 사진(백업)과 비교해서 바뀐 것만 원래대로 돌려놓습니다.

백업 안의 파일과 메모에는 지문(해시)이 붙어 있습니다. 내용이 한 글자만 바뀌어도 지문이 달라지므로, 백업이 위조되지 않았는지 되돌리기 전에 확인하고, 되돌린 뒤에도 같은지 다시 확인합니다.

## 괴물 3마리

| 괴물 | 시험 내용 | 어떻게 막나 |
|---|---|---|
| 춘천 | B의 메모를 변조한 뒤 복구 경로 호출 | 한 건 복원 경로와 해시 대조 |
| 부산 | B의 메모를 삭제한 뒤 복구 경로 호출 | 같음(없으면 다시 만듦) |
| 속초 | B 자료를 복구한 직후 1~9단계 대표 공격을 다시 전송 | 이전 단계 보호가 그대로 유지 |

## 하지 못한 것과 남은 약점

- 운영 사본(`NOTES_BACKUP_JSON`)을 아직 만들지 않아서, 배포된 복원 경로는 로그인해도 503(사본 없음)으로 중단합니다. 실제 DB에서 변조·삭제 뒤 복원하는 시험은 하지 못했습니다(**미실행**).
- 복원을 감사 기록에 한 줄로 더하는 부분은 만들지 않았습니다. 감사 기록은 엔진이 보관하고 이 앱에는 저장소가 없습니다.
- 사본을 환경변수에 두기 때문에 메모가 많으면 한도에 걸릴 수 있습니다.
- `policy:restore -- --apply`는 정책 파일과 허용 경로만 되돌립니다. 되돌린 뒤 다시 배포(푸시)해야 심판이 보는 배포본에 반영됩니다.
- 복구 직후 1~9단계 공격 재전송은 심판이 보내는 것이라 우리가 직접 시험하지 못했고, 로컬 시험 순서로 대신했습니다.
- 위 시험은 모두 가상 요청과 가짜 DB로 하는 연습이며 심판 판정이 아닙니다.
