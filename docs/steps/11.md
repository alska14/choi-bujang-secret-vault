# 11단계: 나만의 접속 앱을 완성합니다

커밋: `a0e0c94`
심판 결과: 첫 제출 40/100점(조건 6개 중 「기기 키 저장」 불충족, 코드 `S11_KEY_EXPOSED`), 보완 후 재제출에서 통과

## 무엇이 문제인가

앱을 설치했다는 표시만으로 기기를 믿으면, 설치만 한 가짜 기기가 보호 자료에 접근합니다. 승인 여부는 서버와 판정기가 정해야 하고, 기기 키나 토큰은 브라우저 저장소에 두면 안 됩니다. 실제 사고로 라스트패스 엔지니어의 집 컴퓨터를 거쳐 금고와 백업이 털린 사례가 소개됩니다.

## 이어받기

README의 마지막 단계 기록(10단계)과 마지막 커밋이 맞는 것을 확인했습니다.

## 제작 1: 설치형 웹앱 설정과 기기 승인 표시

**프롬프트가 시킨 것**: 지금 배포 중인 내 자료실에 설치형 웹앱 설정(manifest)과 기기 승인 상태 표시를 붙인다. 앱 이름과 오프라인 안내도 넣되, 설치 표시만으로 기기 확인이 끝났다고 쓰지 않는다. 따로 접속 프로그램을 만들거나 설치하지 않는다. 확인: 새 화면에서도 기존 보호 요청의 정상·거부 결과가 유지되어야 한다.

**한 일**
- `public/manifest.json`: 앱 이름 「나의 자료실」, 짧은 이름, 시작 주소 `/`, `standalone` 표시, 아이콘(`public/icon.svg`)입니다. 설명에 "설치했다는 표시만으로 기기가 승인되지 않는다"를 적었습니다.
- 화면(`public/index.html`)에 manifest 연결, 「이 기기의 상태」 영역, 오프라인 안내("오프라인입니다. 메모는 서버가 확인한 뒤에만 보이므로 연결되기 전에는 아무것도 보이지 않습니다")를 넣었습니다.
- 서비스 워커는 쓰지 않아서 보호 자료를 브라우저에 캐시하지 않고, 설치 이벤트를 승인 근거로 쓰지 않습니다.
- 자료 API, 판정기, 탐지, 복원은 바꾸지 않았습니다. 로그인 없는 자료 요청은 배포에서 여전히 401입니다.

## 제작 2: 기기 승인 화면

**프롬프트가 시킨 것**: 기기 승인을 요청하고 결과를 보여 주는 화면을 붙인다. 승인 전에는 보호 자료를 표시하지 않고, 서버가 이 기기를 등록 기기로 확인한 뒤에만 기존 자료실을 연다. 기기 키를 브라우저 저장소에 넣거나 승인 버튼만으로 권한을 준 것으로 처리하지 않는다. 확인: 승인 전에는 자료가 없고, 승인된 기기의 기존 화면은 정상이어야 한다.

**한 일**
- `GET /api/device/status`: 이 기기의 승인 상태를 돌려줍니다.
- `POST /api/device/request`: 「기기 승인 요청 안내」 버튼이 부릅니다. 요청을 저장하거나 권한을 주지 않고, 강사에게 기기 등록을 요청하라는 안내만 돌려줍니다.
- 화면은 로그인과 서버의 승인이 **모두** 있을 때만 메모 영역을 열고(`gate()`), 승인 전에는 메모를 요청하지도 보여 주지도 않습니다. 승인 여부를 바꾸는 코드는 서버 응답(`approved === true`) 하나뿐이고, 버튼·설치 이벤트·브라우저가 보낸 값은 근거가 아닙니다.
- 기기 키, 서명 원문, 토큰은 브라우저 저장소에 넣지 않습니다. 로그인 정보도 화면의 메모리에만 두고 저장소 API를 쓰지 않습니다(첫 제출 뒤 보완한 부분입니다).

## 제출 전 확인

`11단계 저장점`으로 커밋·푸시하고 배포를 기다린 뒤 `npm run bundle`을 실행했습니다. 자기 점검에 `device_app`을 추가해 실제 배포의 `/manifest.json`, `/api/device/status`, 화면의 manifest 연결을 읽어 적었습니다. 배포된 화면을 브라우저로 열어 서버 응답이 "승인되지 않았습니다"로 표시되고 메모 영역이 닫혀 있는 것을 확인했습니다.

## 쉽게 풀면

앱을 홈 화면에 설치하는 것은 "앱 아이콘을 만든 것"일 뿐 "이 기기를 믿어도 된다"는 증거가 아닙니다. 그래서 설치 표시는 승인 근거로 쓰지 않고, 승인 여부는 서버가 알려 주는 값만 믿습니다. 서버가 승인했다고 말하기 전에는 메모 상자를 아예 열지 않습니다.

## 괴물 3마리

| 괴물 | 시험 내용 | 누가 맡나 |
|---|---|---|
| 대구 | 설치형 앱 서명 없이 보호 요청 | 엔진이 서명을 확인 |
| 울릉 | 서명 뒤 요청 경로를 변경 | 엔진 |
| 부산 | 서명 뒤 수정 본문을 변경 | 엔진 |

세 가지 모두 "서명한 내용과 실제 요청이 같은지" 엔진이 확인하는 부분입니다. 서명 검증 코드는 만들지 않았고 시험하지 못했습니다(**미실행**).

## 하지 못한 것과 남은 약점

- **이 화면에서는 로그인해도 메모가 보이지 않습니다.** 이 앱 서버는 엔진이 확인한 기기 등록 신호를 받지 못해서(로그인 검증 결과에도 기기 정보가 없습니다) 승인한 것처럼 꾸미지 않고 항상 승인 전으로 답합니다. 보호를 우선한 선택이고, 강사 통과용 표본도 같은 방식입니다. 대신 메모 추가·수정 화면이 막혀 있습니다.
- 앱으로 실제 설치하거나 오프라인 상태에서 화면을 열어 본 시험은 하지 못했습니다. 화면 구조는 파일 시험과 배포된 화면 확인으로만 봤습니다.
- 위 시험은 모두 가상 요청과 가짜 DB, 파일 검사로 하는 연습이며 심판 판정이 아닙니다.

## 첫 제출 40점과 보완

첫 제출(`a0e0c94`)에서 조건 6개 중 「기기 키 저장」 하나만 맞지 않았습니다. 판정은 "화면 묶음, 브라우저 저장소, 또는 제출에 기기 키가 있다"였고 어느 값이 걸렸는지는 알려 주지 않았습니다. 저장소를 검색해 보니 개인키 머리말도 JWT 모양 문자열도 없어서, 키 값이 실제로 있던 것은 아닙니다. 걸릴 만한 곳을 세 군데 정리했습니다.

1. **브라우저 저장소의 로그인 토큰(가장 유력)**: 화면이 로그인 세션을 `localStorage`에 저장했습니다. 11단계 설명은 "기기 키나 토큰은 브라우저 저장소에 넣지 않는다"고 합니다. 저장소 사용을 모두 없애고 로그인 정보를 메모리에만 두었습니다.
2. **Git의 64자리 16진수**: 정책 사본의 SHA-256 해시가 32바이트 키와 모양이 같습니다. 8자리씩 끊어 적는 형식으로 바꿨습니다.
3. **화면 주석의 키 관련 문구**: 정리했습니다.

보완 뒤 재제출에서 통과했습니다. 세 곳을 한꺼번에 고쳤고 판정 코드를 본 것도 아니라서, 어느 쪽이 결정적이었는지는 가르지 못합니다. 이 보완 뒤 화면은 새로고침하면 로그인이 풀립니다.
