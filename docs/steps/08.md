# 8단계: 자료마다 갈 수 있는 구역을 나눕니다

커밋: `031cb72`(저장점), `b2a41c2`(보완)
심판 결과: 첫 제출 36/100점(`S08_OTHER_ZONE_ALLOWED`), 보완 뒤 만점

## 무엇이 문제인가

같은 계정으로 로그인해도 자기 메모, 강사 공지, 다른 사람의 자료를 모두 같은 권한으로 열 수 있으면 도플갱어가 옆으로 번집니다. 실제 사고로 펠로톤 API가 비공개로 설정한 회원 정보까지 내준 사례(2021)가 소개됩니다.

## 이어받기

README의 마지막 단계 기록(7단계)과 마지막 커밋이 맞는 것을 확인했습니다. 이 앱에는 강사 공지 기능이 없다는 것도 확인했습니다.

## 제작 1: 자원 ID로 구역 표시

**프롬프트가 시킨 것**: 내 자료실의 메모와 강사 공지를 서로 다른 자원 ID로 표시한다. 기존 자료와 주소는 보존하고 화면 메뉴 변경은 이번 요청에 넣지 않는다. 확인: 요청마다 서버가 구별할 수 있는 자원 ID가 있어야 한다.

**한 일**
- 판정기(`src/decider.mjs`)에 구역 표 `ZONES`를 만들었습니다. 내 메모(`my-notes`)는 `GET /notes/:id`, `GET /api/notes/:id`, `GET /api/my/notes`, 반 공지(`class-notices`)는 `GET /api/notices`입니다. 둘 다 읽기만 열고, 강사 자료는 열린 경로가 없습니다.
- 첫 제출에서 36점을 받은 뒤, 같은 내용을 `aleph.config.json`의 `allowedRoutes`에도 `{service, method, pathPattern, zone}` 객체로 선언했습니다(보완).

## 제작 2: 판정기의 구역 규칙

**프롬프트가 시킨 것**: 자기 메모 읽기·수정과 강사 공지 수정의 구역 규칙을 판정기에 넣는다. 엔진이 확인한 사용자·기기·메서드·정확한 경로를 쓰고, 알 수 없는 경로는 거부한다. 쿼리로 기능을 고르지 않고 자료 ID만 고르며, `:id`와 같은 깊이에 `export` 같은 기능 경로를 두지 않는다. 이전 규칙은 유지한다. 확인: A의 자기 메모는 허용되고, B가 A의 메모를 요청하는 것과 일반 학생의 공지 수정은 거부된다.

**한 일**
- 표에 없는 경로(전체 목록, 모르는 경로, `export` 같은 기능 경로)는 `route_not_allowed`로 거부합니다.
- 쓰기(POST·PUT·PATCH·DELETE)는 구역과 관계없이 `write_not_allowed`로 거부합니다. 일반 학생의 공지 수정도 여기서 막힙니다.
- 기기 규칙과 재확인 규칙은 그대로 유지했습니다.

**프롬프트와 다르게 한 점**: 프롬프트는 "자기 메모 읽기·수정"이라고 했지만 쓰기를 모두 거부했습니다. 판정 요청에는 메모 주인이나 강사 역할 값이 없어서, 판정기는 "내 메모인지" 확인할 수 없습니다. 강사 통과용 표본도 쓰기를 전부 거부합니다. 본인 메모 수정의 허용 여부는 자료 API의 소유자 비교가 정합니다.

## 제작 3: 자료 API에서 다시 확인

**프롬프트가 시킨 것**: 자료 API에서도 검증된 사용자와 저장된 소유자·강사 권한을 다시 대조한다. 화면 메뉴나 요청 본문의 `role`을 믿지 않고 거부 사유를 짧게 남긴다. 이번에는 API 확인만 추가한다. 확인: 메뉴를 우회한 직접 API 요청에서도 다른 구역 자료가 나오지 않아야 한다.

**한 일**: 4단계부터 있던 소유자 비교(남의 메모는 404 `NOT_FOUND`)를 바꾸지 않고, 시험을 추가했습니다. 본문과 쿼리에 `role`, `owner_id`를 끼워 넣은 직접 요청으로도 B가 A의 메모를 읽거나 고치거나 지우지 못하고, 목록에는 본인 메모만 나옵니다.

## 36점이 나온 이유와 보완

첫 제출에서는 판정기 표는 맞았지만, `aleph.config.json`의 `allowedRoutes`가 구역 없이 쓰기 경로와 전체 목록 경로까지 열고 있었습니다. 심판이 이 값을 `/aleph.json`으로 읽는 것으로 보여서, 강사 통과용 표본처럼 읽기 경로 4개만 구역과 함께 선언하고 `GET /api/my/notes`, `GET /api/notices`(둘 다 읽기 전용)를 실제로 추가했습니다. 보완 뒤 만점이 나왔습니다. 판정자 코드를 본 것이 아니라 표본과 결과를 근거로 한 추정입니다.

## 쉽게 풀면

건물에 층별 출입 구역을 나눈 단계입니다. 내 사무실 구역(내 메모)과 공용 구역(반 공지)은 열람만 되고, 어느 구역이든 서류를 고치는 일은 이 문(판정기)에서는 안 열어 줍니다. 구역표에 없는 문을 두드리면 "그런 문은 없다"고 답합니다.

## 괴물 4마리

| 괴물 | 시험 내용 | 어떻게 막나 |
|---|---|---|
| 여수 | 다른 구역 메모를 API로 조회 | 4단계 소유자 검사(404)와 구역 표 |
| 통영 | 다른 구역 메모를 API로 수정 | 판정기 쓰기 거부, 소유자 검사 |
| 성주 | 다른 구역 메모 목록을 API로 조회 | 전체 목록 경로를 표와 선언에서 제외 |
| 경주 | 학생 시험 계정으로 강사 공지 수정 | 판정기 쓰기 거부, 공지 API는 쓰기 405 |

## 하지 못한 것과 남은 약점

- 엔진 경로에서는 추가·수정·삭제와 전체 목록이 열리지 않습니다. 화면(`public/index.html`)이 쓰던 `GET /api/notes`는 선언에서 빠졌지만 코드와 4단계 소유자 검사는 남아 있습니다. 화면은 이번 요청 범위 밖이라 손대지 않았습니다.
- 이 앱에는 저장된 공지 자료가 없습니다. `GET /api/notices`는 로그인한 사용자에게 빈 목록을 돌려줍니다. 강사 역할 값은 계약에 없어서 역할로 여는 코드는 없습니다.
- 실제 배포에서 다른 계정으로 직접 API를 불러 본 시험은 하지 못했고, 가짜 인증·가짜 DB 시험만 했습니다.
