# 5단계: 요청을 서버 한곳으로

> 이 단계는 이전 작업에서 진행했습니다(커밋 `d0d70bd`, 보완 `4c30d60`). 제작 프롬프트 원문은 이번 기록 작업에서 보지 못해서, README의 기록을 근거로 정리했습니다. 제작 번호는 나누지 않았습니다.

## 무엇이 문제인가

브라우저에 Supabase 공개 키가 있어서, 서버 함수를 거치지 않고 DB 주소를 직접 부를 수 있었습니다.

## 한 일

- 브라우저는 Supabase를 직접 부르지 않고 서버 함수 `/api/auth`, `/api/notes`만 부릅니다. 화면 코드에는 공개 키(`sb_publishable_…`)도 SDK도 없습니다. 키는 서버 환경변수(`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`)에만 둡니다.
- `/api/auth`(`src/auth-api.mjs`)가 로그인, 가입, 토큰 갱신, 로그아웃을 대신 받습니다. 브라우저에는 `access_token`, `refresh_token`, `expires_at`, `email`만 돌려줍니다.
- `db/revoke-direct.sql`로 `notes` 테이블의 `public`, `anon`, `authenticated` 직접 권한을 모두 회수했습니다. 서버 함수는 서버 전용 키(`service_role`)로 접속해서 영향이 없습니다. RLS와 정책은 이중 방어로 남겼습니다.
- 쿼리 없는 원본 자료 주소를 `aleph.config.json`의 `originalApiUrl`에 적고, 빌드가 `/aleph.json`에도 `originalApiUrl`, `allowedRoutes`, `identityProvider`(비밀값 없음)를 기록합니다. 설정에만 적고 `/aleph.json`에 안 옮기면 심판이 `S05_ORIGINAL_URL_MISSING`으로 거부합니다(보완 커밋 `4c30d60`이 이 부분을 고쳤습니다).

## 쉽게 풀면

금고 뒷문을 막은 단계입니다. 경비원이 서는 정문(서버 함수)으로만 드나들게 하고, 뒷문(DB 직접 접근)은 열쇠를 회수해서 잠갔습니다.

## 확인한 방법 (2026-10-06)

- 권한 회수 전에는 `authenticated`에 SELECT·INSERT·UPDATE·DELETE가 있었고, 회수 후에는 `anon`, `authenticated` 모두 권한이 없으며 `service_role`만 남았습니다(서버 역할이 6건을 읽음).
- 공개 키로 원본 REST 주소를 직접 부르면 HTTP 401 `permission denied for table notes`가 나옵니다. 키 없이 불러도 401입니다.
- 배포 화면 코드에서 `sb_publishable`, `sb_secret`, SDK 문자열을 검색한 결과 0건이었습니다.
- 배포된 `/api/auth`에 틀린 비밀번호로 로그인하면 Supabase의 `Invalid login credentials`가 400으로 돌아옵니다(서버에서 Supabase로 가는 경로 확인). 가입 요청은 계정이 생겨서 보내지 않았습니다.

## 하지 못한 것

로그인한 A·B의 실제 토큰으로 앱을 쓴 시험은 실행하지 않았습니다.

## 남은 약점

- `/api/auth`는 로그인 없이 부를 수 있는 공개 주소이고 자체 횟수 제한이 없어서, 비밀번호 대입 방어를 Supabase Auth의 기본 제한에 기댑니다.
- 로그인 토큰이 브라우저 `localStorage`에 저장되어, 화면에 스크립트가 주입되면 읽힐 수 있습니다. (11단계 보완에서 저장소 사용을 없애고 메모리에만 두도록 바꿨습니다.)
- 주인 없는 메모 한 건, 옛 공개 커밋 `93f6d0e`와 옛 배포의 과거 노출은 그대로입니다.
- 화면 코드에서 지운 공개 키는 3단계 커밋부터 Git 이력에 남아 있습니다. 공개용 키이고 `notes` 직접 권한을 회수해서 쓸 수 없지만, 이력까지 지운 것은 아닙니다.
