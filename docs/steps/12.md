커밋: `6ade2e0`(저장점), `38162c8`(문서), 이후 점검 대기 시간 보완
심판 결과: 통과. 앞선 제출은 「확인하지 못했습니다」 두 번, 23점, 38점, 「확인하지 못했습니다」(38점, `UNV_AMBIGUOUS`) 순이었고 여섯 번째 제출(커밋 6df2243)에서 통과했습니다

## 무엇이 문제인가

1~11단계를 따로 확인했어도, 총공세에서 서로 다른 규칙이 충돌하면 일부 공격이 통과하거나 정상 사용자까지 막힐 수 있습니다. 확인 결과가 흩어져 있으면 무엇을 실제로 확인했고 무엇을 안 했는지 알 수 없고, 화면의 "성공" 문구만 믿게 됩니다. 실제 사고로 에퀴팩스가 패치를 놓치고 만료된 인증서 때문에 76일간 침입을 알아채지 못한 사례가 소개됩니다.

마지막 총공세는 12단계 통과와 41종 공격 방어로 판정하고, 차별화는 가산 과제입니다. 괴물 3마리는 다음과 같습니다.

| 괴물 | 시험 내용 |
|---|---|
| 광주 | 무인증 조회와 타인 메모 조회를 같은 제출본에 연속 전송 |
| 천안 | 미등록 기기 요청 뒤 회수된 신원으로 다시 전송 |
| 양양 | 복구 뒤 서명 없는 변경 요청과 구역 밖 조회를 전송 |

## 이어받기

README의 마지막 단계 기록(11단계 보완)과 마지막 커밋이 맞는 것을 확인했습니다. 강사 통과용 표본을 보니 12단계는 점검 기록을 읽는 작전실 화면과, 점검 결과에 「막음」「미실행」을 구분해 적는 방식이었습니다. 우리 저장소는 `artifacts/submission.json`을 커밋하지 않는 규칙이라, 작전실은 서버 함수가 실제 API를 직접 불러서 그 결과를 보여 주는 방식으로 만들었습니다.

## 제작 1: 탈환 작전실 화면

**프롬프트가 시킨 것**: 탈환 작전실에 판정기 규칙, 탐지 사건, 회수 상태, 복구 버전의 요약을 보여 준다. 실제 API 응답에서 확인된 결과와 미실행을 구분하고 가상 메모 본문은 표시하지 않는다. 확인: 화면의 수치와 가린 서버 기록이 서로 맞아야 한다.

**한 일**
- `public/ops.html`: 판정기 규칙(개수와 이름), 복구 버전(검증한 정책 사본의 버전·검증한 커밋·현재 정책과의 차이), 점검 요약, 정상·금지 요청 표를 보여 줍니다. 서버 값은 `textContent`로만 그리고 브라우저 저장소를 쓰지 않습니다. 성공 문구는 없습니다.
- `GET /api/ops`(`api/ops.js`, `src/ops-api.mjs`, `src/ops-checks.mjs`): 화면의 모든 수치는 이 서버 기록에서 옵니다. 항목마다 종류를 구분합니다.
  - `live_api`: 배포 주소에 실제 HTTP 요청을 보내 받은 응답 상태로 판단한 결과(로그인 없는 목록, 엉터리 토큰, 쿼리·헤더에 끼워 넣은 신원, 원본 자료 주소, 공지 수정, 복원, 위조한 기기 승인 헤더 등 12개)
  - `code_run`: 판정기와 탐지 함수를 가상 요청으로 직접 실행한 결과(등록·미등록 기기, 복합 이상 접속, 구역, 조회 폭주 등)
  - `not_run`: 실행하지 않은 시험
- 응답에는 가상 메모 본문과 토큰이 없고, 응답 본문은 저장하지 않으며 상태 코드와 기대 여부만 남깁니다.
- `vercel.json`에 `api/ops.js`가 정책 사본과 정책 파일을 읽을 수 있도록 포함 파일을 지정했습니다.

## 제작 2: 정상·금지 요청 표 만들기

**프롬프트가 시킨 것**: 1~11단계의 정상·금지 요청, 기대 결과, 실제 API 결과, 요청 ID, 확인 시각을 한 표로 만드는 절차를 붙인다. 아직 실행하지 않은 41종 시험을 임의로 통과 처리하지 않는다. 확인: 금지 요청 거부와 정상 요청 허용이 모두 실측 결과로 남아야 한다.

**한 일**: `npm run verify:table`(`scripts/verify-table.mjs`)을 만들었습니다.
- 표의 열은 단계, 종류, 요청, 기대, 실제, 요청 ID, 확인 시각, 결과입니다. `artifacts/verify-table.json`(커밋하지 않는 폴더)에도 저장합니다.
- 요청마다 새 UUID를 `x-request-id` 헤더로 보내고 같은 값을 표에 적습니다.
- 정상 요청(본인 목록 읽기 허용, B가 A의 메모를 읽으면 거부)은 시험 계정 토큰(`VERIFY_TOKEN_A`, `VERIFY_TOKEN_B`)이 있을 때만 실행합니다. 읽기 요청만 보내고 토큰과 메모 본문은 출력하지도 저장하지도 않습니다. 토큰이 없으면 「미실행」입니다.
- 총공세 41종은 심판이 실행하는 시험이라 「미실행」으로 둡니다. 임의로 통과 처리하지 않습니다.

**하지 못한 것**: 정상 요청의 실제 허용 결과는 시험 계정 토큰이 없어서 실행하지 못했습니다. 토큰을 넣어 한 번 실행하면 채워지는 구조만 만들어 두었습니다.

## 제작 3: 설치·실행·중지·복구 안내

**프롬프트가 시킨 것**: 검사한 커밋을 기준으로 학생 판정기·탐지 규칙·접속 앱·자료실의 설치·실행·중지·복구 안내를 README에 적는다. 엔진은 ALEPH SDP 엔진 사용으로 출처를 밝히고 비밀값은 포장하지 않는다. 확인: 학생 몫과 제공 엔진의 출처가 구분되고 재현 순서가 있어야 한다.

**한 일**: README의 12단계 절에 다음을 적었습니다.
- 출처 표: 학생이 만든 것, 시작 틀에서 온 것, 제공 엔진(ALEPH SDP 엔진 사용, 엔진 코드는 이 저장소에 없음), 외부 서비스(Supabase, Vercel, TypeSafe Jev)를 구분했습니다.
- 환경변수는 이름만 적고 값은 적지 않았습니다.
- 설치, 실행, 점검, 중지, 복구의 순서와 재현 순서를 적었습니다.

## 쉽게 풀면

지금까지는 방마다 자물쇠를 따로 확인했다면, 12단계는 건물 관제실을 만드는 단계입니다. 관제실 화면에는 "다 잘 됐습니다"라는 문구 대신, 확인한 것(실제로 문을 두드려 본 것), 장부로만 확인한 것(규칙을 직접 돌려 본 것), 아직 안 한 것(미실행)이 표로 나옵니다. 안 한 것을 한 것처럼 적지 않는 게 핵심입니다.

## 하지 못한 것과 남은 약점

- 총공세 41종, 시험 계정 토큰으로 하는 정상 요청과 B의 접근 거부, 운영 사본으로 하는 복원은 실행하지 못했습니다(표에 「미실행」으로 남음).
- 작전실의 「기대대로」는 우리가 정한 기대와 맞는다는 뜻이며 심판 판정이 아닙니다.
- 작전실 서버 함수는 배포 주소에 요청을 보내므로 응답이 느리면 일부 항목이 「미실행」이 될 수 있습니다.
- 11단계는 첫 제출 40점(`S11_KEY_EXPOSED`) 뒤 보완해서 통과했습니다. 다만 11단계의 항상 승인 전 상태(화면에서 메모가 보이지 않음)는 그대로입니다.

## 첫 제출 「확인하지 못했습니다」와 보완

심판이 격리 환경에서 명령을 끝내지 못해(`UNV_RUN_ENVIRONMENT`) 12단계를 확인하지 못했습니다. 원인은 확인하지 못했습니다. 우리 쪽에서 의심해 볼 수 있는 부분으로 자기 점검(`src/attack-check.mjs`)의 대기 시간을 줄였습니다.

- 12단계에서 실제 요청 점검이 순서대로 하나씩 기다리는 구조로 늘어, 응답이 느리면 최대 대기가 약 110초(11단계는 약 60초)였습니다. 10~12단계의 실제 요청 점검 3개를 처음에 동시에 시작하고, 각각 네트워크 오류를 잡아 「미실행」으로 남기도록 했으며, 대기 시간을 8초(작전실은 15초)로 줄였습니다.
- 응답이 없는 주소로 돌려 보니 수정 전후 모두 첫 점검(로그인 없는 목록 요청)에서 10초 만에 끝났습니다. 그래서 이 보완이 이번 증상의 원인을 고쳤다고 말할 수는 없습니다. 네트워크가 완전히 막힌 경우는 원래부터 빨리 끝났고, 이번처럼 일부 요청만 느린 경우의 대기를 줄인 정도입니다.
- 판정 화면 안내대로 잠시 뒤 다시 제출합니다. 같은 결과가 이어지면 강사에게 알립니다.

## 재제출에서도 「확인하지 못했습니다」와 점검 방식 변경

첫 제출과 재제출 모두 판정이 「확인하지 못했습니다」(`UNV_RUN_ENVIRONMENT`, 점수 0/100, 판정 화면은 "실패가 아니며 학생 잘못이 아닐 수 있다"고 안내)였습니다. 원인은 확인하지 못했습니다. 다만 강사 통과용 표본(`byteback-sample-pass`)의 2026-10-11 커밋(「12단계 묶음을 현재 runner 증거에 맞춤」)을 비교해 보니, 우리 점검이 옛 방식이라 runner가 응답을 독립적으로 관측할 근거가 없었을 가능성이 있어 표본의 방식에 맞췄습니다. 심판 코드를 본 것이 아니라 표본과 문서를 근거로 한 추정입니다.

- **증거 표식**: 점검이 보내는 모든 요청의 `fetch` 옵션에 `alephEvidence: { caseId, requestKey: 'read' }`를 붙입니다. 요청 헤더나 주소에는 넣지 않습니다. 읽기(GET) 요청만 보냅니다.
- **규칙 사례 경로**: `GET /api/checks?case=<사례>`(`api/checks.js`, `src/checks-api.mjs`, `src/rule-check.mjs`)가 고정된 가상 입력으로 판정기·탐지 규칙을 실행하고 `{ready, decision, reasonCode}` 또는 `{ready, action}`을 돌려줍니다. 사례는 `s06-unregistered`, `s07-compound`, `s08-unknown-route`, `s08-all-notes`, `s08-write-notice`, `s09-burst-read`입니다. 모르는 사례나 배열은 400(`unknown_check`)이고, 사용자 입력을 코드로 실행하지 않습니다. `ready`는 가상 조건에서 기대한 판정이 나왔다는 뜻이며 실제 사용자 기기의 승인 상태가 아닙니다. 사례 없이 부르면 작전실과 같은 점검의 요약 수치(`total`, `blocked`, `failed`, `notRun`)를 돌려줍니다.
- **점검 결과 형식**: `attackId`, `stage`, `expected`, `observed`, `result`(`blocked`, `breached`, `not_run`) 다섯 키만 담습니다. 요청을 보내지 못하면 `not_run`이고 「막음」으로 세지 않습니다. `scripts/bundle.mjs`도 같은 형식을 검증하고 `checkedAt`을 기록합니다.
- **대기 시간 상한**: 점검 19개를 동시에 시작하고 요청마다 8초로 제한합니다. 응답이 없는 주소로 돌려 보면 오류 없이 8초 만에 끝나고 18개가 `not_run`으로 남습니다(이전 구조는 첫 점검에서 오류로 중단).
- 1단계 설정으로 부르면 옛 동작(`/data.json` 확인)을 유지합니다(`test/r5.test.mjs`).
- 시험(`test/checks.test.mjs` 7개)은 가짜 배포로 형식·증거 표식·읽기 요청만 보냄·메모 본문 비기록·네트워크 오류 처리를 확인합니다.

- 작전실이 자기 자신을 부르는 순환 호출을 없앴습니다(점검 목록에서 작전실 점검을 뺌).
- 정상 요청의 허용을 보여 주는 규칙 사례(`s08-own-note`)를 추가했습니다.
- 시험 계정 토큰이 없어 보내지 않은 정상 요청 2개를 점검 목록에 미실행으로 넣었습니다(통과로 세지 않음). 점검 항목은 20개(막음 18, 뚫림 0, 미실행 2)입니다.

원인은 모두 판정 문구와 표본을 근거로 한 추정이며 심판 코드를 본 것이 아닙니다. 어느 수정이 결정적이었는지는 재제출 결과를 봐야 알 수 있습니다.

## 네 번째 제출: 38점, 조건 2개 불충족

수치 일치(`S12_SCREEN_MISMATCH`)는 해결되어 점수가 23점에서 38점으로 올랐습니다. 남은 것은 출처 구분(`S12_SOURCE_MIXED`)과 실제 API 결과(`S12_SLOGAN_AS_PASS`)입니다. 두 조건의 내용은 이미 README 에 적었는데도 맞지 않았습니다.

원인으로 본 것은 심판이 그 내용을 읽지 못했을 가능성입니다. 판정 코드를 본 것이 아니라 길이를 비교한 추정입니다.

| 비교 | 우리 README | 강사 통과용 표본 README |
|---|---|---|
| 길이 | 405줄, 49KB | 64줄, 6.5KB |
| 출처 표 위치 | 333번째 줄 | 10번째 줄 |
| 구성 | 시작 틀 설명 뒤에 1~12단계 기록이 이어짐 | 출처 표, 설치·실행·중지·복구, 점검 기록 순서 |

`AGENTS.md` 도 저장점마다 README 를 "짧게" 갱신하라고 합니다. 그래서 README 를 120줄·13.8KB 로 줄이고 핵심을 앞쪽에 모았습니다. 출처 표는 처음 1.5KB 안에, 설치·실행·중지·복구는 3.4KB 안에, 실측 결과 표는 3.7KB 지점에서 시작합니다. 긴 단계별 기록은 버리지 않고 `docs/STEP_RECORDS.md` 로 옮겼습니다(Git 이력 보존). 제출 칸의 "한 일" 글에도 출처 구분과 실제 응답을 직접 적었습니다.

## 다섯째·여섯째 제출: 형식 맞추기 뒤 통과

다섯째 제출은 38점에 「확인하지 못했습니다」(`UNV_AMBIGUOUS`)였습니다. 점수 문제가 아니라 점검 기록 형식이 심판 규칙과 달라 응답을 대조하지 못한 것입니다.
