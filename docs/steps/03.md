# 3단계: 진짜 로그인

> 이 단계는 이전 작업에서 진행했습니다(커밋 `4c6f5fa`). 제작 프롬프트 원문은 이번 기록 작업에서 보지 못해서, README의 기록을 근거로 정리했습니다. 제작 번호는 나누지 않았습니다.

## 무엇이 문제인가

`/api/notes`를 로그인 없이 누구나 부를 수 있어서, 가상 메모 네 건이 그대로 돌아왔습니다.

## 한 일

- 화면(`public/index.html`)에서 Supabase Auth 이메일·비밀번호로 가입, 로그인, 로그아웃을 합니다.
- 서버가 `src/verify-login.mjs`(수정하지 않은 틀 파일)로 요청의 `Authorization: Bearer` 토큰을 검사합니다. 토큰이 없거나 검사에 실패하면 401과 `{"error":"UNAUTHENTICATED"}`를 돌려주고 자료는 주지 않습니다.
- 브라우저가 보낸 사용자 ID나 역할은 믿지 않고, 검사로 확인한 사용자 ID만 씁니다.
- 검사에 쓰는 발급자 정보는 `aleph.config.json`의 `identityProvider`에 있습니다(비밀 키 없음).
- 자료 API 경로를 `allowedRoutes`에 적었습니다.

| 경로 | 동작 |
|---|---|
| `GET /api/notes` | 로그인한 사용자의 메모 배열 |
| `POST /api/notes` | 추가 |
| `GET /api/notes/:id` | 한 건 조회 |
| `PUT /api/notes/:id` | 수정 |
| `DELETE /api/notes/:id` | 삭제(204) |

## 쉽게 풀면

금고 앞에 경비원을 세운 단계입니다. 신분증(토큰)이 없거나 가짜면 문 앞에서 돌려보냅니다. 다만 신분증이 진짜이기만 하면 누구든 들어올 수 있어서, 남의 서랍까지 열 수 있는 문제는 아직 남아 있습니다.

## 확인한 방법

- 가짜 인증과 가짜 DB로 시험했습니다: `node --test test/notes-api.test.mjs`.
- 배포 뒤 로그인 없이 `/api/notes`를 요청해 401이 나오는지 봅니다.

## 남은 약점

- 로그인한 B가 A의 메모 ID를 알면 읽고 고치고 지울 수 있었습니다. 4단계에서 막았습니다.
- 로그인은 신원 확인일 뿐 권한 구분이 없습니다.
- 이 단계의 점검(`src/attack-check.mjs`)은 로그인 없는 요청만 보냈고, 로그인한 A·B 계정 시험은 실행하지 않았습니다.
- 옛 공개 커밋 `93f6d0e`와 옛 배포의 과거 노출은 그대로입니다.
